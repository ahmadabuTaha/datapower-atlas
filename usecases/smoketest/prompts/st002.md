Shared / Default Object Interpretation
STG-Replica may reuse shared or default DataPower objects.
Do not assume that a reused object is erroneous merely because it is not uniquely named for the service.
Examples can include:
	•	default/shared XML Manager
	•	shared match objects
	•	common TLS / crypto profiles
	•	reusable processing dependencies
	•	other shared platform objects
A shared/default reference is valid configuration evidence when it resolves correctly.
Do not classify it as a GAP or EXPECTED_UNRESOLVED merely because multiple services use it.
Only classify it as unresolved when the referenced object genuinely cannot be resolved from the available evidence.
Names are hints, not evidence.
Routing and Script Semantics
Do not assume the configured MPGW/WSP backend is necessarily the actual operation egress.
If processing actions set behavior such as:
	•	skip-backside
	•	dynamic routing
	•	routing variables
	•	GatewayScript urlopen
	•	XSLT-driven routing
	•	other programmatic outbound calls
follow the actual evidenced execution path.
If a referenced script or stylesheet is required to determine routing behavior, inspect only that resolved file.
Distinguish clearly between:
	•	configured backend
	•	actual evidenced operation egress
	•	candidate route
	•	unresolved route
	•	remote topology that is not evidenced
Do not draw two backend calls merely because both a configured backend and a script-mediated outbound call exist.

Evidence Certainty
Preserve certainty throughout the entire chain.
A downstream skill must not strengthen evidence without new evidence.
Maintain distinctions such as:
	•	confirmed
	•	candidate
	•	unresolved
	•	not_evidenced
Examples:
configured backend ≠ confirmed runtime invocation
hostname ≠ confirmed remote system identity
shared object reference ≠ missing object
configuration presence ≠ runtime success
TLS profile assignment ≠ successful TLS handshake
Do not invent missing topology.
