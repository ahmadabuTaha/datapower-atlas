# DataPower Atlas Codex Smoke Test — ST-001

We are starting the first DataPower Atlas Codex smoke test. Work entirely inside the existing project directory.

Use the repository's existing:

- `AGENTS.md`
- skill contract
- Codex skills
- generated Atlas outputs
- STG User Journey outputs
- supporting indexes and flattened CSVs
- raw DataPower configuration only when verification is required

Do not redesign the existing pipeline before running the test.

## Objective

Run a single-service smoke test for the STG domain to validate whether Codex can move from the generated User Journey evidence to:

1. Correct AS-IS service reconstruction
2. Functional capability decomposition
3. Replacement requirements and solution roles
4. Evidence-faithful PlantUML architecture output
5. A short audit of retrieval behavior and evidence usage

The smoke test must primarily validate the Codex operating model, not rerun the entire Atlas analysis.

## Critical Retrieval Rule

Start from the generated STG User Journey outputs.

Expected retrieval sequence:

```text
STG User Journey → target service journey → operation journeys only when required
→ referenced supporting evidence only when required
→ raw CFG only for unresolved, contradictory, or verification-critical evidence
```

Do **not** begin by loading or independently reconstructing the service from all flattened CSVs. The User Journey is the primary compact retrieval surface.

Supporting flattened CSV or index evidence may be consulted only when:

- the User Journey references something requiring deeper inspection;
- an evidence relationship is unresolved;
- an apparent contradiction exists; or
- additional provenance is required.

Raw CFG remains authoritative and must only be opened when verification is necessary.

## Target Selection

Inspect the STG User Journey outputs and select **one** suitable service. Prefer a representative service that exercises several of the following without requiring excessive evidence retrieval:

- ingress or listener;
- processing policy;
- one or more operations;
- routing or backend behavior;
- security, TLS, or crypto references;
- transformations or scripts;
- file or configuration dependencies; and
- unresolved or candidate evidence, if available.

Do not select the largest or most complex service merely to maximize coverage. Record the selected service and why it was chosen.

## Required Skill Flow

Use the existing skills and contracts. Primary execution flow:

```text
trace-service
→ trace-operation only where necessary
→ datapower-semantics only where interpretation is required
→ investigate-gap only where a real gap or contradiction exists
→ capability-analysis
→ replacement-analysis
→ generate-architecture-diagrams
```

Do not bypass evidence-certainty rules. A downstream skill must not strengthen evidence certainty unless new evidence was explicitly collected.

Preserve these distinctions:

- `confirmed`
- `candidate`
- `unresolved`
- `not_evidenced`

Do not infer missing backend, routing, dependency, or topology. Names are hints, not evidence.

## AS-IS Analysis

Produce an evidence-based reconstruction of the selected service. Cover only what the evidence supports, including where applicable:

- service identity;
- ingress or listener;
- processing policy;
- operations;
- match, rule, and action flow;
- routing or backend behavior;
- transformations or scripts;
- security dependencies;
- file dependencies;
- configuration dependencies;
- unresolved relationships; and
- architectural findings.

Do not make the architecture cleaner than the source configuration. Do not treat an unresolved relationship as an error unless evidence proves it is one.

## Capability Analysis

Convert observed service behavior into functional capabilities. Capabilities must describe what the service actually does; do not use DataPower object names as capabilities.

Examples:

- listener evidence → ingress capability;
- explicit backend routing → backend integration or routing capability;
- XSLT or GatewayScript → transformation or scripting capability; and
- TLS or crypto references → transport security capability.

Do not jump directly from object type to replacement product. Keep findings separate from capabilities.

## Replacement Analysis

Translate validated capabilities into replacement requirements using this chain:

```text
Current Function → Capability → Relevant NFR / constraint
→ Replacement Requirement → Solution Role
```

Mention candidate technology only when clearly useful and supported by the analysis. Do not perform direct mappings such as `MPGW → Product X → Product Y`. A single DataPower service may require multiple replacement solution roles.

## Diagram

Use the existing diagram skill to generate at least one evidence-based service or component diagram in PlantUML. A service-journey diagram is optional if supported without excessive retrieval.

The diagram must preserve certainty and use visually distinct relationships for:

- confirmed;
- candidate; and
- unresolved.

Do not invent missing systems or backend topology. The diagram must never appear more certain than the underlying evidence.

## Smoke-Test Output Location

Create a dedicated smoke-test output directory automatically. Use a lightweight structure similar to:

```text
smoke-tests/STG/ST-001-<selected-service>/
├── smoke-test.md
├── retrieval-log.md
└── service-component.puml
```

Add a second PlantUML file only if genuinely useful. Do not create unnecessary directories or duplicate evidence files, and do not copy existing Atlas CSVs or User Journey data into the smoke-test directory.

## `smoke-test.md`

Create one concise but complete report containing:

1. **Selected Service** — domain, service, and reason selected.
2. **AS-IS Trace**
3. **Capability Analysis**
4. **Replacement Requirements / Solution Roles**
5. **Findings / Evidence Gaps**
6. **Smoke Test Verdict**

Assess retrieval discipline, AS-IS correctness, evidence-certainty preservation, capability decomposition, replacement reasoning, diagram fidelity, and token/context efficiency.

Use one overall state:

- `PASS`
- `PASS_WITH_FINDINGS`
- `INVESTIGATION_REQUIRED`
- `FAIL`

Explain the verdict briefly.

## `retrieval-log.md`

Keep this intentionally short. Record meaningful retrieval stages rather than every file accessed. For example:

```text
START: STG User Journey → selected service
SUPPORTING RETRIEVAL: operation journey → operation X
SUPPORTING RETRIEVAL: relationship/index evidence → dependency Y
RAW CFG: NOT OPENED
```

If raw CFG is opened, record why:

```text
RAW CFG: OPENED
Reason: User Journey and supporting indexes were insufficient to verify the route.
```

Also explicitly note any unnecessary broad retrieval.

## Important Constraints

- Start from STG User Journey outputs.
- Do not load the whole project into context.
- Do not load all CSVs merely because they exist.
- Do not read the whole raw CFG.
- Filter and retrieve narrowly.
- Reuse upstream skill outputs downstream.
- Avoid repeating the same evidence in each analysis stage.
- Preserve evidence provenance and certainty.
- Do not change existing parsers, taxonomy, mappings, or extraction logic unless a concrete reproducible defect blocks completion.
- Record potential defects or coverage gaps as findings instead of immediately redesigning the pipeline.

## Final Goal

This test is successful if Codex demonstrates:

```text
User Journey first → targeted evidence retrieval → correct AS-IS
→ capability decomposition → replacement requirements
→ faithful architecture diagram
```

with minimal unnecessary context loading.

Begin the smoke test now.
